# MLB 每日賽事趨勢篩選（MLB Sports Trends）

抓取 covers.com 的 MLB 賽前趨勢，以「**過盤命中率**」篩選出當日推薦，
產生一頁純靜態的繁體中文儀表板，由 GitHub Actions 每天自動更新並發佈到 GitHub Pages。

**線上網址**：<https://johnny1713.github.io/mlb-sports-trends/>

零外部依賴（純 Python 標準庫），不需安裝任何套件。

> 前端則另外用到 Google Fonts 與 covers.com 的球隊 logo，兩者都不阻塞畫面、
> 失效時也只是換系統字型／隱藏 logo，不會壞版。（logo 曾評估內嵌，實測 gzip 會多
> 49 KB 且是加在會阻塞的 HTML 主文件上，反而拖慢首屏，故維持外部載入。）

## 這個網站在做什麼

使用者在台灣，每天約 **22:00（台灣時間）** 用手機打開網站，依推薦在 playsport.cc 下注。
因此有兩個貫穿整份設計的前提：

- **只看會不會過盤，不看 ROI／Units**。covers 的 ROI 是用美國賠率（-110 那種）計算的，
  對台灣運彩玩家沒有意義，所有 ROI 顯示已於 2026-07-10 全面移除。
- **手機優先**。UI 改動一律先確認窄螢幕不會橫向溢出。
- **開賽時間直接給主場當地時間與台灣時間**（例如 `🕒 當地 7:05 PM ｜ 台灣 8/21 08:05`）。
  covers 給的是美東時間，但使用者在台灣、而「下午場」的判定又是看主場當地時間，
  畫面上只寫美東時間兩邊都對不起來。台灣時間一定帶日期，因為美東晚場對應台灣隔天凌晨。

## 推薦怎麼算

排序統一使用**過盤命中率的 Wilson 90% 信賴下界**（z=1.28），網頁上稱為「**保守命中率**」。

covers 的趨勢文字長這樣：`hit the Game Total Under in 32 of their last 45 games`。
直接看 71% 會被小樣本騙——`4 of last 5` 也是 80%。Wilson 下界會依樣本數自動打折：

| 原始紀錄 | 表面命中率 | 保守命中率 |
|---|---|---|
| 32/45 | 71% | 61.8% |
| 29/50 | 58% | 49.0% |
| 4/5 | 80% | 51.4% |

判讀門檻（網頁上有說明列與顏色）：**≥55% 強訊號（綠）· 50~55% 普通（黃）· <50% 僅供參考（灰）**。

展開單場卡片的「完整詳細趨勢數據」可以看到該場所有原始趨勢，已全部中譯，例如
`多倫多藍鳥 最近 35 個客場有 21 場過「讓分」`（少數翻不出來的句子會顯示 covers 原文）。

其他規則：

- 樣本數 < 8 場的趨勢不參與媒合。
- **大小分**：雙方球隊在同一方向（都看好 Over 或都看好 Under）才成立，分數取兩隊下界平均。
- **勝負／讓分盤**：一隊強勢（High）搭配對手弱勢（Low），分數 =（強隊過盤率下界 + 對手不過盤率下界）/ 2。
- 首五局（F5）與 Team Total 趨勢**刻意排除**，只做全場市場。
- **讓分盤一律以標準 ±1.5 呈現**。covers 的盤口表列的是各家運彩公司報價，裡面會混入
  alternate run line（±2.0／±2.5／±3.0），個別莊家還會把主客欄位的正負號寫反。
  covers 自己的讓分趨勢統計是以 ±1.5 算的，因此只採信 ±1.5、以多數決決定讓分方；
  判斷不出來時只顯示「讓分／受讓」不帶數字，寧可不顯示也不顯示錯的。
- 下午場判定依**主場當地時間**（當地 17:00 前開打），不是美東時間。

## 近期走勢（Recent Form）：只顯示，不計分

covers 每場另外提供 8 條 Recent Form 趨勢，與上面的 ROI Trends 是不同來源。
它們**只作參考顯示，永遠不列入評分與排序**，原因是實測 64 條的統計：

- 樣本數只有 4~9 場，而且 **64 條裡有 60 條是 0 敗**。
- 套用同一套 Wilson 下界，**64 條全部 ≥55%**（57.5%~84.6%），一旦混入排序會把
  真正有樣本厚度的趨勢全部擠掉。
- 這些是 covers 在同一場比賽試過大量條件切法（as a favorite／vs. a right-handed starter／
  after allowing 2 runs or less…）之後挑出來的全勝切片，**選擇偏誤對 Wilson 是隱形的**。
- 資料本身就自相矛盾：8 場裡有 5 場同時出現 Over 與 Under 的全勝紀錄。

網頁上的用途只有兩個，都不影響分數：

1. 單場卡片的「📈 近期走勢（僅供參考）」清單（已中譯；條件子句如「休息 4 天時」
   「對戰 WHIP 高於 1.30 的先發投手」「對戰主場戰績不到五成的球隊」都會翻，
   只有主審／投手姓名保留英文）。
2. 推薦上的「✅ 走勢同向／⚠️ 走勢反向」旁證標記。

**市場涵蓋範圍**：該區只有大小分與球隊**直接勝負**，完全沒有讓分資料。
因此讓分盤的標記是由直接勝負推得，並分兩級強度——受讓 +1.5 直接獲勝必定過盤（有效佐證）；
讓分 -1.5 還需贏 2 分以上，標為「較弱」（實測 30 隊獨贏命中率與讓分過盤率相關係數僅 0.407）。

## Top 5 精選清單的組成

網頁最上方是「AI 智慧精選 Top 5」，下方另有勝負／讓分與大小分兩份 Top 5。組成規則：

- **保守命中率低於 50% 的一律不上榜**。網站自己把 <50% 標示為「僅供參考」，
  讓它進精選等於自打嘴巴。冷門日寧可列不滿 5 筆、甚至整區掛零（會明確顯示原因）。
- **同場同隊只留分數最高的一筆**。「買 X 獨贏」與「買 X 讓 1.5」是同一個看法的兩種風險版本，
  兩筆都上榜等於浪費名額。單場卡片不受影響，仍完整顯示。
  （大小分不需要這道手續：單場最多只會產出 1 筆，兩隊同時湊得出「都看好大分」與
  「都看好小分」時，源頭就只保留分數高的那個方向。）
- **只排除真正互斥的同場推薦**，以分差建模判斷（獨贏需 ≥1 分、讓 1.5 需 ≥2 分、受讓 1.5 需 ≥-1 分）。
  押不同隊不等於矛盾——「買 A 獨贏」＋「買 B 受讓 1.5」在 A 贏 1 分時同時成立。
- **排序只看保守命中率**；近期走勢僅在分數完全相同時決勝（Top 5 邊界經常是平手，
  而同分時原本是由 covers 的賽事列表順序決定，那是任意的）。低分不會被走勢拉到高分前面。
- Top 5 下方有「👀 差一點進 Top 5」區塊：走勢同向、分數與門檻差 ≤3 分**且** ≥50% 的落榜推薦，
  最多 5 筆，沒有符合者整區隱藏。
  **這區大多數日子是空的，屬正常現象**——實測 27 天只有 2 天開出東西。
  要同時滿足「落榜、分數仍 ≥50%、與門檻差距在 3 分內、近期走勢又同向」本來就罕見。
  冷門日門檻貼近 50% 時，窗口會被 50% 下限壓到接近 0，結構上就不會有。

## 過往命中率（頁面最底部）

網站會累積自己的戰績：每輪把當天的推薦與前一天的比分存進 `history.json`，
在頁面最下方顯示一個**預設收合**的「📊 過往命中率」區塊。

| | 內容 |
|---|---|
| 最近一次結算 | 昨日 AI Top 5 的逐筆結果（✅／❌）與命中數 |
| 近 30 天 / 全期間 | AI Top 5 合計，以及依盤口（獨贏／受讓 1.5／讓 1.5／大分／小分）拆開 |
| 分組比較 | 依時段（下午場 vs 非下午場）、依近期走勢（同向 vs 未同向） |
| 每一格 | 命中率、**分母**、以及**保守命中率**（與推薦卡片同一套 Wilson 下界） |

分母和保守值都和百分比一起顯示，是因為 17 筆的 41% 和 170 筆的 41% 完全是兩回事，
只寫百分比很容易把雜訊當訊號。

**這一區純粹顯示，不影響任何推薦與排序。** 和 Recent Form 同樣的理由：
用三位數的樣本回頭調參數，過擬合的風險遠大於訊號。
另外，命中率是「有沒有過盤」的紀錄、**不含賠率**——命中率高不等於賺錢。

資料從 **2026-07-10** 起算。那天修掉了「分析已完賽比賽」的 bug，
在那之前有 39.6% 的場次在頁面標示日期之前就已經打完，那段期間的命中率不是預測能力。

## 自動更新

`.github/workflows/scrape.yml` 每天跑 6 輪（UTC 11:17／12:17／13:17／15:17，
加上 16:17／17:17 兩輪補救），跑完直接 commit `index.html`，GitHub Pages 隨即重新部署。

多輪的原因：

- GitHub Actions 的排程實測會延遲 1~2.5 小時。
- covers 的趨勢是賽前漸進發佈的（美東清晨 5 點幾乎全空，8 點半左右大致發滿），
  太早跑會拿到大量空白。
- 補救輪專門處理 covers 延遲到美東中午才發佈的日子（2026-08-01 就發生過，
  當天前四輪全部撲空）。

### 網頁會分辨三種「沒東西看」的情況

這三件事意義完全不同，不能混用同一句話帶過：

| 情況 | 網頁顯示 |
|---|---|
| covers 還沒發佈趨勢 | ⏳ covers.com 尚未發佈今日趨勢，稍後的自動更新會補上 |
| 趨勢有了，但沒有推薦達到 50% | 😴 今日沒有達標的推薦——這是正常結果，不是資料出錯 |
| 有幾場沒抓成功 | ⚠️ 今日有 N 場沒有抓取成功（賽事列表共 X 場，實際分析 Y 場） |

最後一項尤其重要：抓取失敗以前是**完全靜默**的——該場會整場從當日資料消失，
網頁上毫無跡象，你只會看到今天少一場，無從分辨是漏抓還是當天本來就沒這場比賽。

> 注意：內容沒變就不會產生 commit。連續多輪都抓到空資料時輸出位元組相同，
> 於是不 commit、Pages 不重新部署，看起來像整天沒更新。
> 要確認是否真的有跑，請看 Actions 執行紀錄，不要看 commit 紀錄。

### 部署失敗的自動補救

GitHub Pages 的部署偶爾會失敗（2026-08-06 一天四次掛了三次——但那天 GitHub 有
Actions／Pages 的全站故障，不是日常頻率）。單看一次失敗還好，但和上面那條疊起來會變成
**無限期卡住**：
部署失敗後，下一輪若抓到相同內容就不 commit，也就不會再觸發部署，
網站可以一直停在舊頁面而毫無跡象——那天就卡過使用者 22:00 的看盤時段。

因此 workflow 在「這輪沒有產生新 commit」時，會抓一次線上頁面與剛產出的檔案比對 sha256，
不一致就補一個空 commit 逼 Pages 重新部署。看到 `Redeploy: Pages 頁面落後於 main`
這種 commit，就代表前一次部署失敗、系統自己救回來了。

## 本機執行

```powershell
# 抓今日（美東日期）賽事
python scrape.py

# 抓指定日期
python scrape.py --date 2026-05-28

# 只重新產生頁面，不連網（改版面／樣式時用）
python scrape.py --replay
```

執行後會覆寫專案根目錄的 `index.html`，直接用瀏覽器開啟即可預覽。

`--replay` 會從既有 `index.html` 內嵌的 JSON 讀回資料重畫，**0.3 秒**完成。
完整爬蟲要發 16 次請求、約一分鐘，只為了看一行 CSS 的效果並不值得，也沒必要
多打擾 covers 一次。因為輸入輸出是同一份資料，**行為沒變時產出會位元組完全相同**，
所以它也能拿來驗證「只改樣板」的重構有沒有改壞東西。

## 已知限制

- 資料完全仰賴 covers.com，對方改版或延遲發佈都會直接反映在網站上。
- 趨勢本身是 covers 篩選過的結果，不是完整母體，因此保守命中率是**相對比較**用的排序依據，
  不能當成真實勝率的估計。
- MLB 休賽期（10 月底~3 月）**連續 60 天無 commit 會讓 GitHub 自動停用排程**，
  隔年開季要到 Actions 頁面手動 re-enable。
